# Text engine

**What this page is for.** Touching anything a string passes through on its way to the screen —
buffers, placeholders, the charmap, fonts, msgbox types. [[dialogue-voice]] covers what a line should
*say*; this page covers the machinery that will silently mangle it. The one-paragraph model: a string
is a byte array in a proprietary single-byte encoding, `0xFF`-terminated, walked by exactly one
renderer that blits one variable-width glyph per tick — **no word wrap, no auto-pagination, no
overflow error**. Text past the window edge is clipped mid-glyph, silently, which is why almost every
rule below ends in "and a static check must catch it before the build" (record 45 §0, §4.6). See
[[verification-discipline]].

---

## 1. Three buffers, one destination, and no `{POKEMON}`

**There is no `{POKEMON}` or `{ITEM}` placeholder.** Species, item, move, trainer names are not
placeholders at all — a script must first copy them into a buffer with a `buffer*` command
(`bufferspeciesname`, `bufferitemname`, `buffermovename`, and the rest of the family) and then
reference the buffer as `{STR_VAR_n}`. This is the single most common structural misunderstanding
carried over from Gen-3 binary-hacking tutorials (record 45 §2.3, §3.2).

The buffers are exactly these:

| Buffer | Bytes | Role |
|---|---|---|
| `gStringVar1/2/3` | 256 each | the only three substitutable slots — `{STR_VAR_1..3}` |
| `gStringVar4` | 1000 | **the composed destination, not a fourth variable** |
| `gDisplayedStringBattle` | 425 | the battle-side destination |

Field dialogue always expands the template into `gStringVar4` and prints `gStringVar4`. A
`{STR_VAR_4}` constant does not exist in the charmap and would be a build error (record 45 §2.1).

**Battle strings reuse the `0xFD` prefix over a colliding id space.** `FD 01` is `{PLAYER}` in a
field string and `B_BUFF2` in a battle string; a different expander resolves battle ids into
`gDisplayedStringBattle`. The two id spaces overlap numerically, so **a string is valid in exactly
one of the two contexts** — a field placeholder in a battle string, or vice versa, produces garbage
with no error (record 45 §2.4).

### 1.1 The cheap lint targets

None of the copy primitives bound-check the destination, and every one of these is statically
visible in a script file (record 45 §2.2, §2.6, §3.2):

- **`bufferstring` is an unbounded copy.** A literal over 255 bytes walks straight out of
  `gStringVar1` into `gStringVar2`.
- **`stringvar` ids ≥ 3 index off the end.** The script-side array has exactly three entries and the
  macro passes any literal id through unchecked, so `bufferitemname 3, …` writes past the array.
- **Expansion recurses with no cycle detection** — a buffer whose contents contain `0xFD` bytes
  expands again.
- **The composed message has a 1000-byte ceiling** — a long template plus three full 255-byte
  buffers overruns `gStringVar4`.
- The one *good* case: a single literal over **1024 mapped bytes is a build error**, caught by the
  preprocessor, not a truncation (record 45 §1.1).

## 2. The charmap: you author in UTF-8, the build maps it

Source strings are written in **UTF-8** and translated to the proprietary single-byte table at build
time; `é`, `♀`, `“…”` are typed literally, and an unmapped codepoint is a **hard build error**, not
mojibake (record 45 §1.1). The rules an author actually hits:

- **ASCII `"` and `\` have no charmap entry — both are build errors.** Use the typographic quotes
  `“ ” ‘ ’`, which is what all vanilla dialogue does. `\'` *is* legal — it maps the ASCII apostrophe
  to the right typographic quote `’` (record 45 §1.7, correction 4).
- **`_` silently renders as a hyphen.** Deliberate in the engine (it exists for label-derived
  autogenerated strings), but in dialogue it is a typo that renders without complaint (record 45
  correction 4).
- **Terminators split by language.** In `.inc` assembly you type the terminator yourself as `$`. In
  C, `_("…")` appends `0xFF` automatically — an inner `$` double-terminates — and `__("…")`
  deliberately appends nothing (record 45 correction 5).

## 3. Measurement traps

`GetStringWidth` is the engine's own measuring stick, and it lies in three specific ways
(record 45 §4.5):

1. **It returns 0 for any string containing `{PLAYER}`, `{RIVAL}`, or any placeholder other than
   `{STR_VAR_1..3}`.** Only the three buffer ids are dereferenced; everything else hits a
   `default: return 0`. Engine callers that centre or auto-shrink text treat such a string as
   zero-width — the auto-fit helper never narrows a `{PLAYER}` string, because it always "fits".
   **Always measure the expanded `gStringVar4`, never the template.**
2. **It splits only on `\n`.** `\l` and `\p` do not reset the accumulator, so a multi-page message
   measures as the *concatenation* of its pages, not its widest line. Any measurement tool must
   split on all three break bytes.
3. The same bogus zero fires for an unknown font id and for a mid-string `{FONT}` naming an unknown
   font — three distinct causes of a width of 0, none of them an error.

And one property that shapes every width calculation: **`letterSpacing` is inert for Latin text.**
The advance is exactly the glyph-width table entry; the inter-letter gap is baked into the glyph
bitmaps, and the spacing parameter applies only to Japanese text and keypad icons. A width
calculator that adds a per-character gap is wrong (record 45 §4.4).

### 3.1 Editing a glyph is two uncoupled edits

A font's art and its metrics live in different files that nothing reconciles (record 45 §4.9):

- **The art**: `graphics/fonts/latin_<font>.png` — 256 × 512 px, 16 × 16 px cells, 512 glyphs
  indexed directly by charmap byte.
- **The widths**: a hand-maintained `u8[512]` array per font in `src/fonts.c`.

They are not derived from each other. Editing the PNG cell without the matching array index — or
the reverse — produces overlapping or gappy text **with no error at build or runtime**. One asset
trap on top: seven of the eight Latin font PNGs are stored at 2 bpp, but **`latin_small.png` alone
is 4 bpp** — any tool that assumes 2 bpp fails on exactly that file (record 45 §4.9).

## 4. msgbox lock/release is asymmetric

The `msgbox` types do not share one lock discipline, and a lint for "`lock` without `release` =
permanent player freeze" must model each type (record 45 §3.2):

| Type | Locks? | Releases? |
|---|---|---|
| `MSGBOX_NPC` | `lock` | `release` |
| `MSGBOX_SIGN` | `lockall` | `releaseall` |
| `MSGBOX_DEFAULT` | no | no |
| `MSGBOX_YESNO` | no | no |
| `MSGBOX_AUTOCLOSE` | **no** | **`release`** |

**Only `MSGBOX_NPC` and `MSGBOX_SIGN` are self-balancing.** `MSGBOX_AUTOCLOSE` is the trap: it
releases without ever locking, because it is designed to run *inside* a caller's own `lock`. A lint
that models it as self-contained wrongly flags the caller's `lock` as unmatched; a lint that models
it as locking misses a genuine double-release when the caller also writes `release`.
